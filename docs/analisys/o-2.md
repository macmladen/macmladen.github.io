## 2. Criteria

From your stated goals, in priority order:

1. **The sites are the portfolio.** The stack choice is itself a deliverable, not only a tool.
2. **Editing is not a second job.** Admin UI, drafts, preview, media library. No YAML front-matter surgery for a typo.
3. **Technically clean.** One language, one runtime, current versions, no legacy ecosystem tax.
4. **Skills transfer.** To client work and to the planned React Native app.
5. **One person maintains all of it.** Marginal cost of site #4 must approach zero.

One mailing list, segmented by interest, owned by you — not four lists. It is the asset that survives brand changes.

## 4. Stack recommendation

### Core

| Layer | Choice | Version (Aug 2026) |
|---|---|---|
| Front-end | Next.js, App Router | 16.2.x |
| CMS | Payload 3, self-hosted | 3.x |
| Language | TypeScript, end to end | 5.x |
| Styling | Tailwind v4 + CSS-variable design tokens | 4.x |
| DB | Neon (serverless Postgres) | — |
| Media | Cloudflare R2 (S3-compatible, no egress fees) | — |
| Monorepo | pnpm workspaces + Turborepo | — |
| Hosting | Vercel (Next apps), Cloudflare DNS | — |
| Email | Resend (transactional) + Buttondown (list) | — |
| Analytics | Plausible or Umami — EU-hosted, no cookie banner | — |
| Podcast | Transistor or Captivate; site consumes RSS | — |
| Mobile | Expo SDK 57 (RN 0.86, React 19.2) | — |

### Why Payload

It is a TypeScript-native CMS that runs inside a Next.js app. You define collections in TS config; it generates the admin panel, REST API, GraphQL API, a Local API (direct, no HTTP hop when co-located), and TypeScript types for all of it. ([Figma blog](https://www.figma.com/blog/payload-joins-figma/))

Against your criteria:

- **Portfolio.** It is the same architecture as decoupled Drupal — content API plus JS front-end — in a current form. The capability story survives the change of backend, and it demonstrates schema design, access control, hooks and custom admin work rather than site-building in someone else's UI.
- **Editing.** Real admin: drafts, versions, live preview, scheduled publish, shared media library. This is the requirement that eliminates a git-file CMS (Keystatic, Tina, Decap) as the primary system — those are fine for a developer editing a developer's site and poor for anything else.
- **Clean.** One language, one dependency graph, one deploy pipeline. No PHP runtime, no OAuth consumer dance, no JSON:API schema drift between two type systems.
- **Transfer.** The React Native app consumes the same API with the same generated types. Payload also supplies auth and collections, so the app does not need a second backend. A Drupal backend gives that app a PHP-shaped API and no shared types — this is the argument that decides it.

**Operational note:** Payload Cloud stopped taking new sign-ups after the Figma acquisition, so self-hosting is required. That is Vercel + Neon + R2, which is the recommendation regardless.

**Alternative worth considering: Sanity.** Better on ops — hosted content lake, no database or media storage to run, built-in image CDN, best-in-class editing. You trade: you own less of the stack (weaker portfolio claim), and the mobile app would need a separate backend for anything stateful. If the ops load of Payload turns out to be the thing that stalls this, Sanity is the correct fallback and the content model transfers.

### Why Next rather than Astro

Astro is the better technical fit for pure content sites — less JavaScript shipped, faster by default. It loses on three of your criteria: no Payload Local API, no shared React component model with the RN app, and a weaker market signal. If the sites were only marketing pages I would say Astro. Given they are portfolio and feed a mobile app, Next.

### Repo layout

```
apps/
  cms/          Payload 3 + Next — admin + API, own deploy
  macmladen/    Next 16
  bluefish/     Next 16
  razgovori/    Next 16
  koder/        Next 16
packages/
  ui/           components + design tokens (per-brand token files)
  content/      typed client — the only module that talks to the CMS
  config/       eslint, tsconfig, tailwind preset
```

`apps/cms` standalone rather than embedded in `apps/macmladen`: admin stays available independent of front-end deploys, editing content does not rebuild the personal site, and the multi-site architecture is explicit and demonstrable. Cost is one extra Vercel project.

**The seam:** `packages/content` is the only place that fetches. Pages never call the API directly. Week 1 it reads MDX from disk; week 2 it reads Payload. That makes the CMS a swap rather than a prerequisite, which is what keeps the site launch off the CMS's critical path.

### Design tokens

One source of truth in `packages/ui` (TS object) generating both CSS custom properties for web and a theme object for React Native via NativeWind. Per-brand override is one file: accent hue, display face, radius scale. This is what makes site #3 and #4 a weekend each.

## 5. Opinion on Drupal and WordPress

**For your own sites: neither.** Both add a PHP runtime, a database, and a security-update cadence to serve content volumes measured in dozens of items. Both give the mobile app an API with no shared types. Drupal's editorial strength is multi-editor, multilingual, complex-workflow publishing — none of which describes a one-person operation for the next 18 months.

**As a portfolio argument:** decoupled Drupal demonstrates a skill whose buyers are Drupal shops and enterprise/public-sector integrators. That is a real market, and if you want it, one client case study proves it better than your own site does. The TypeScript full-stack story addresses a wider market and matches the ecosystem-agnostic positioning behind the conference plan.

**As client offerings: keep both.** WordPress is where regional volume is; Drupal is where regional enterprise and public-sector budgets are. Neither needs to run on your own domain to be sellable. Keep the DDEV/Drupal setup parked on a branch — it costs nothing and it is a working reference.

**Secondary effect worth naming:** "I evaluated decoupled Drupal, chose a TS-native stack, and here is the threshold at which I would go back" is stronger talk and case-study material than a decoupled Drupal walkthrough, and it is consistent with a conference that is deliberately not tied to one CMS.

## 6. Content model

Small and shared across all sites. A `site` relationship field on content, not five separate instances.

| Collection | Fields (core) |
|---|---|
| `sites` | key, name, tokens, domain |
| `pages` | site, slug, blocks, SEO |
| `posts` | site, slug, body, tags, publishedAt |
| `talks` | title, event, date, location, slidesUrl, videoUrl, abstract |
| `projects` | client, role, stack, summary, outcome, year |
| `episodes` | number, guest, summary, audioUrl/RSS guid, transcript |
| `people` | name, bio, links — guests, clients, co-authors |
| `media` | shared library |
| `redirects` | from, to, status |

Page blocks: hero, prose, feature grid, quote, CTA, logo strip, embed. Seven blocks, not twenty. Add one when a page needs it.
